# [Phase 3 회고록] TDD 기반 엣지 케이스 검증 및 AI 논리적 환각 제어 (Post-mortem)

## 1. 개요
본 회고록은 3차시(Day 9 ~ Day 12) 동안 진행된 'AI 산출 로직의 엣지 케이스 검증' 및 '테스트 주도 개발 사이클을 통한 로직 수선' 과정에서의 핵심 트러블슈팅과 철학적 통찰을 기록한다.

## 2. 관찰 및 교훈: AI 시대의 테스팅 패러다임 전환
* **AI 바이브 코딩의 2가지 맹점:** AI에게 로직 구현을 맡길 경우, 주어지는 데이터가 항상 완벽할 것이라고 가정하는 **'해피 패스 편향'**과, 당장 눈앞의 프롬프트나 에러만 통과하기 위해 전체 도메인 규칙을 무시해버리는 **'논리적 과적합'** 현상이 뚜렷하게 관찰되었다.
* **TDD의 재정의:** 과거의 테스팅이 인간 엔지니어의 '타이핑 실수'를 잡기 위한 안안망이었다면, 본 실험을 통해 증명된 **AI 시대의 테스팅은 "LLM이 현실 세계의 비즈니스 규칙을 맘대로 왜곡하지 못하도록 통제하는 실행 가능한 명세서이자 목줄"**이다. 실패하는 테스트를 먼저 작성하여 가드레일을 치는 방식이 가장 강력한 환각 제어 수단임을 입증했다.

## 3. 기술 트러블슈팅 및 의사결정 로그

### Issue 1: 가맹점명 파편화 및 Null 방어 실패
* **현상:** 대소문자가 혼용된 결제 내역(`Netflix`, `netflix`, `NETFLIX`)을 AI는 모두 다른 가맹점으로 인식하여 정기구독 클러스터링에 실패함. 또한, 사용자의 결제 내역이 아예 없는 빈 리스트(Empty List) 주입 시 NPE 발생 위험 노출.
* **해결:** `transactions.stream().collect(Collectors.groupingBy(...))` 과정에 `.trim().toUpperCase()` 정규화 파이프라인을 강제로 주입하여 데이터 파편화를 방어함. 또한 메서드 최상단에 `Collections.emptyList()` 반환을 통한 조기 종료(Early Return) 로직을 추가하여 안정성을 확보함.

### Issue 2: 금액 오차율을 무시한 단일 그룹화 알고리즘의 한계
* **현상:** 넷플릭스 요금이 10,000원에서 10,500원으로 인상되자, AI가 작성한 단순 `groupingBy` 로직은 1원 단위의 엄격한 비교로 인해 이를 완전히 다른 결제 건으로 분리해버림(탐지 실패).
* **해결:** 단순히 값이 같냐 다르냐를 따지는 멍청한 비교를 폐기함. 대신 이전 결제액 대비 오차율(10%)을 계산하여 유동적으로 그룹에 편입시키는 **'±10% 오차 허용 클러스터링 알고리즘'**을 인간 엔지니어가 직접 설계하여 주입하고 교정함.

### Issue 3: 시간적 맥락 누락
* **현상:** 90일이 훌쩍 지난 1~2년 전의 폐기용 결제 데이터까지 모두 긁어모아 현재의 유효한 정기결제로 오판하는 도메인 규칙 누락 현상 발견. AI는 현실 세계의 '시간적 제약'을 스스로 유추하지 못함.
* **해결:** `VALID_PERIOD_DAYS = 90`이라는 상수를 도입하고, `isBefore()`를 활용한 데이터 필터링 파이프라인을 구축하여 기계에게 '비즈니스의 시간적 맥락'을 강제함.

### Issue 4: AI의 억지 논리와 FSM 붕괴
* **현상:** AI가 작성한 `cancel()` 메서드는 겉보기엔 작동하는 듯했으나, 미사용 의심 상태(`WARNING`)가 아니면 무조건 에러를 던지는 기괴한 억지 논리로 작성되어 있었음. 심지어 정상 이용 상태인 `CONFIRMED` 상태값은 아예 누락됨.
* **해결:** 누락된 상태값을 복구하고, `DETECTED` (해지 불가) ➔ `CANCELED` (종료) 등 엔지니어가 1차시에 설계했던 올바른 상태 전이 다이어그램에 맞추어 예외 처리 방어 로직을 전면 리팩토링함.

## 4. 알려진 한계 및 향후 과제
* **테스트 코드의 함정:** Issue 4의 사례처럼 AI가 짠 억지 로직이 우연히 테스트를 통과하더라도, 그 내부 논리를 뜯어보면 실제 비즈니스 규칙과 심각하게 모순될 수 있음을 확인했다.
* **결론 및 과제:** TDD가 AI의 환각을 통제하는 훌륭한 도구임은 맞으나, 테스트가 통과했다고 해서 코드를 맹신해서는 안 된다. 결국 **'엔지니어의 꼼꼼한 코드 리뷰'**가 최종적으로 결합되어야만 기술 부채 없는 완벽한 소프트웨어를 릴리즈할 수 있다.

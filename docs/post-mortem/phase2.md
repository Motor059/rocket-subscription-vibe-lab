# [Phase 2 회고록] UI 상태 설계의 가치 및 통합 트러블슈팅 (Post-mortem)

## 1. 개요
본 회고록은 2차시(Day 5 ~ Day 8) 동안 진행된 '프론트엔드 컴포넌트 아키텍처 설계' 및 'Spring Boot 백엔드 API 통합' 과정에서의 핵심 관찰 결과와 Troubleshooting 과정을 기록한다.

## 2. 관찰 및 교훈: UI 상태 설계가 사용자 경험(UX)과 아키텍처에 미치는 영향
* **Case A (명세 부재 시):** 화면 구현에만 초점을 맞춘 AI 바이브 코딩은 데이터 로딩(Loading), 데이터 공백(Empty), 통신 지연 및 에러(Error) 등의 예외 상태를 전혀 방어하지 못했다. 이는 사용자가 빈 화면이나 무의미한 에러 창을 마주하게 만들어 극심한 UX 저하를 초래했으며, 모든 예외 처리를 단일 파일(`App.tsx`)에 몰아넣는 기술 부채를 양산했다.
* **Case B (4대 UI 상태 명세 주입 시):** 사전에 Loading, Success, Empty, Error 상태에 대한 디자인 및 컴포넌트 분리 명세서를 강제한 결과, 백엔드 API와의 통신 실패나 FSM 상태 전이 위반(400 Bad Request) 시에도 사용자에게 명확한 에러 안내(Error State)와 재시도 버튼을 제공하여 애플리케이션의 신뢰도와 UX를 비약적으로 상승시켰다.

## 3. 기술 트러블슈팅 및 의사결정 로그 (Post-mortem)

### Issue 1: Jackson 라이브러리의 Boolean 네이밍 파싱 함정
* **현상:** 프론트엔드에서 '해지하기' 액션 트리거 시 `{"isCancelAction": true}`를 전송했으나, 백엔드에서 이를 `false`로 파싱하여 FSM이 의도치 않은 `IGNORED` 상태로 강제 전이되는 치명적 버그 발생.
* **원인:** Spring Boot의 Jackson JSON 파서가 JavaBean 규약에 따라 `isCancelAction` 필드명에서 `is`를 임의로 제거하고 `cancelAction`이라는 Key를 기대하면서 발생한 직렬화/역직렬화 불일치.
* **해결:** `SubscriptionActionRequest` DTO 내 해당 필드에 `@JsonProperty("isCancelAction")` 어노테이션을 명시하여 프론트엔드의 JSON 규약과 백엔드 파싱 규약을 강제로 일치시킴으로써 데이터 무결성을 회복함.

### Issue 2: 배치 스케줄러의 멱등성 결함
* **현상:** 해지(CANCELED)된 구독 가맹점이 배치 재탐색 실행 시 새로운 구독(DETECTED)으로 중복 인서트되어 부활하는 현상 발생.
* **원인:** 과거 트랜잭션을 기반으로 패턴을 분석하는 로직 특성상, 이미 상태가 종료된 가맹점이라도 과거 결제 이력이 존재하면 신규 구독으로 오인함.
* **해결:** `SubscriptionService`의 탐지 로직 최종 단계에, DB에 이미 존재하는 가맹점 이름(상태 불문)일 경우 영속화 대상에서 제외하는 필터링 로직을 추가하여 배치 시스템의 멱등성을 확보함.

## 4. Known Issue (알려진 한계 및 향후 과제)
* **재구독 시나리오와 Soft Delete의 딜레마:** 위 'Issue 2'에서 중복 탐지를 막기 위해 `findByUserId`로 전체 내역을 조회해 필터링을 걸어둔 결과, 사용자가 해지(`CANCELED`)한 이후에 다시 정기 결제를 시작하더라도 이를 새로운 구독으로 탐지하지 못하는 논리적 맹점이 발견됨.
* **향후 개선 방향:** 이는 단순한 버그가 아닌 "스팸 방지(알림 최소화)"와 "재구독 탐지" 사이의 비즈니스 정책 딜레마임. 향후 기획 단계에서 활성화된 상태의 구독만 필터링하도록 로직을 개선하거나, 재구독 유예 기간 정책을 도입하는 방향으로 고도화가 필요함.

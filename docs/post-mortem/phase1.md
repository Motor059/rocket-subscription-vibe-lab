# [Phase 1 회고록] 요구사항 명세의 가치 및 백엔드 도메인 모델링 (Post-mortem)

## 1. 개요
본 회고록은 1차시(Day 1 ~ Day 4) 동안 진행된 '로켓 구독 시스템 백엔드 도메인 아키텍처 설계' 및 '유한 상태 기계(FSM) 기반 비즈니스 로직 구현' 과정에서의 정량적 비용 변화와 Troubleshooting 과정을 기록한다.

## 2. 관찰 및 교훈: 요구사항 명세 유무가 토큰 소모와 코드 품질에 미치는 영향
* **Case A (명세 부재 시):** 요구사항과 규칙이 정의되지 않은 모호한 아이디어 상태에서 AI에게 곧바로 구현을 지시한 결과, 비결정론적 특성으로 인한 심각한 환각(Hallucination) 현상이 관찰되었다. 주기성 분석 로직의 임의 변형, 예외 처리 누락, 유기적 관계가 붕괴된 스파게티 코드가 산출되었으며, 이를 수정하기 위한 프롬프트 재입력 과정에서 컨텍스트가 누적되어 비용이 기하급수적으로 낭비되는 실패를 경험했다.
* **Case B (도메인 모델 및 FSM 주입 시):** 구현 전에 유스케이스 다이어그램과 상태 다이어그램을 통해 시스템 가드레일을 명확히 선언하고 프롬프트에 주입했다. 그 결과, 단 1회의 코드 생성만으로 도메인의 제약 조건을 완벽히 만족하는 무결한 엔티티와 서비스 레이어가 도출되었다. 엄격한 사전 설계 명세에 투자한 약간의 초기 토큰이 소프트웨어 생명주기 전체의 유지보수 비용을 극적으로 절감함을 정량적으로 입증했다.

## 3. 기술 트러블슈팅 및 의사결정 로그

### Issue 1: 무분별한 Setter 사용으로 인한 FSM 상태 전이 무력화 위험
* **현상:** 초기 설계 시 외부 레이어에서 `subscription.setStatus()`를 통해 아무런 제약 없이 구독 상태(`DETECTED`, `WARNING`, `CANCELED`, `IGNORED`)를 강제 변경할 수 있는 데이터 오염 가능성 식별.
* **원인:** 객체 지향의 캡슐화 원칙을 위반하고 엔티티를 순수 데이터 구조체처럼 취급함으로써, 비즈니스 규칙(예: `DETECTED`에서 즉시 `CANCELED`로 건너뛰는 전이 불가능 규칙)을 영속성 계층에서 방어할 수 없었음.
* **해결:** `Subscription` 엔티티의 무분별한 수정자(Setter)와 기본 생성자를 무력화(`access = AccessLevel.PROTECTED`)함. 상태 변경 권한을 엔티티 내부의 전용 비즈니스 메서드(`updateToWarning()`, `cancel()`, `ignore()`)로 격리하고, 허용되지 않은 상태 전이 시도 시 `IllegalStateException`을 던지도록 강제하여 도메인의 무결성을 완벽하게 방어함.

### Issue 2: 대량의 금융 결제 데이터 조회로 인한 힙 메모리 과부하(OOM) 리스크
* **현상:** 구독 주기를 판단하기 위해 사용자의 결제 내역(`Transaction`)을 조회하는 과정에서, 가입 기간이 긴 사용자의 가맹점 데이터를 무조건 전체 조회할 시 서버 메모리가 고갈되는 OutOfMemoryError(OOM) 발생 가능성 감지.
* **원인:** 데이터베이스 쿼리의 탐색 범위(Boundary) 제약 조건이 명세되지 않아, 주기성 분석에 불필요한 수년 전의 단건 결제 데이터까지 영속성 컨텍스트에 모두 로드되는 설계 결함 존재.
* **해결:** 주기성 분석에 필요한 타임라인의 가드레일을 '최근 90일'로 정의하고, `TransactionRepository`에 `findByUserIdAndTransactionDateAfter` 메서드를 구현하여 불필요한 데이터 조회를 원천 차단함. 더불어 데이터베이스 레이어에 `(user_id, transactionDate, merchantName)` 복합 인덱스(`@Index`)를 설정하여 성능 최적화까지 동시 달성함.

### Issue 3: 다양한 구독 주기(연간/주간) 확장에 따른 시스템 부하 트레이드오프
* **현상:** 정기 결제는 30일 기준의 월간 구독뿐만 아니라, 특정 이커머스의 연간 회원권(365일)이나 주간 정기 배송(7일) 등 다양한 주기를 가짐. 초기 모델링 시 이를 모두 탐지 알고리즘에 포함할지 고민함.
* **분석:** 만약 연간 구독을 자동 탐지하려면, 알고리즘(`SubscriptionDetector.java`)의 판단 주기 윈도우를 365일 이상으로 늘려야 하며, 이는 필연적으로 DB에서 Fetch해야 할 `Transaction` 데이터의 조회 기간을 '최근 90일'에서 '최소 2년(730일)'으로 대폭 확장해야 함을 의미함. 이는 앞서 Issue 2에서 도출한 OOM 리스크 및 DB 부하 완화 조치와 정면으로 충돌함.
* **의사결정:** MVP 단계의 한계와 자원 효율성을 고려하여, 가장 빈번하게 발생하는 **'월간(25~40일) 구독'으로 도메인 바운더리를 의도적으로 스코핑(Scoping)하여 축소**함. 연간 구독 등 장기 패턴은 자동 탐지 엔진에 무리를 주지 않도록 향후 '사용자 수동 등록 기능'을 추가하거나, 월간 배치와 분리된 '연 1회 장기 배치 스케줄러'를 별도로 도입하는 아키텍처 확장 계획으로 남겨둠.

## 4. Known Issue (알려진 한계 및 향후 과제)
* **결제 금액의 동적 변동성(±10%) 흡수 한계:** 현재 `SubscriptionDetector` 분석 알고리즘은 정기 구독의 강력한 특징인 '동일 금액 반복'에 의존하여 금액별 그룹화(`groupedByAmount`)를 수행함. 그러나 통신사 할인, 글로벌 환율 변동, 서비스 가격 인상 등으로 인해 동일 가맹점의 결제 금액이 미세하게 요동칠 경우, 동일 정기 결제 패턴임에도 독립된 단건 결제로 오인하여 탐지에 실패하는 한계가 존재함.
* **향후 개선 방향:** 다음 단계 리팩토링 시, 완벽한 금액 일치 조건 대신 가맹점별 정렬 후 결제일 간 격차(25~40일)를 우선 검증하고, 금액 오차 범위를 상단 백엔드 분석 설계 스펙에 맞춰 유동적으로 허용하는 정밀 클러스터링 알고리즘으로의 고도화가 요구됨.

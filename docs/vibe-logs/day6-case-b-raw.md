# [Day 6] 프론트엔드 Case B (명세 기반) 바이브 코딩 및 아키텍처 대조 로그

## 1. 실험 개요
- **일시:** 2026년 5월 24일
- **목적:** 4대 UI 상태 명세와 컴포넌트 트리 구조 설계도를 AI에게 사전 주입했을 때, 프론트엔드 아키텍처(결합도/응집도)와 UX 품질이 어떻게 변화하는지 Case A와 대조 분석.

## 2. 입력 프롬프트 (Prompt) 요약
```text
1. 백엔드 API 계약(TypeScript Interface) 제공
2. 4대 UI 상태(Loading, Success, Empty, Error) 명세 제공 (해피 패스 차단)
3. 7개의 역할별 컴포넌트 트리 분리 제약 조건 제공 (God Component 차단)
위 명세를 100% 준수하여 분리된 컴포넌트 코드를 산출할 것.
```

## 3. AI 출력 결과 (성공작 - 가드레일 완벽 준수)
**[아키텍처 및 UX 개선 포인트]**
1. **SRP(단일 책임 원칙) 기반 컴포넌트 분리:** 단일 `App.tsx`에 몰려있던 코드가 `DashBoardPage.tsx` (상태 관리), `MobileLayout.tsx` (레이아웃), `WarningCard.tsx` (도메인 UI) 등 7개의 파일로 완벽히 분리됨.
2. **해피 패스(Happy Path) 탈피:** `Spinner` 컴포넌트와 `Error` 분기 처리가 기본적으로 탑재되어, 네트워크 지연 및 실패 상황에서도 사용자 경험(UX)을 방어함.
3. **FSM 동기화 보장:** 프론트엔드가 임의로 상태를 덮어씌우지 않고, 백엔드 API(`PATCH`)의 성공 응답을 확인한 후 UI를 업데이트(동기화)하도록 구현됨.

## 4. 프론트엔드 2차시 최종 대조 분석 (A vs B)
| 구분 | Case A (명세 부재) | Case B (엄격한 설계 명세) |
| :--- | :--- | :--- |
| **누적 토큰 비용** | **약 4,650 토큰 초과** (잦은 유지보수 및 프롬프트 핑퐁) | **약 2,500 토큰** (단 1회 호출로 설계도 100% 구현) |
| **아키텍처 구조** | God Component (`App.tsx` 단일 파일에 강결합) | SRP 준수 (7개 계층적 컴포넌트로 분리, 높은 응집도) |
| **예외 처리 (UX)** | 해피 패스 편향 (Loading, Error, Empty 처리 누락) | 4대 UI 상태 완벽 방어 |
| **결론** | 화면 구현만 지시하면 유지보수가 불가능한 기술 부채가 양산됨. | **UI 상태와 컴포넌트 위계 명세에 토큰을 투자하면 배포 가능한 엔터프라이즈급 프론트엔드 코드가 산출됨.** |
